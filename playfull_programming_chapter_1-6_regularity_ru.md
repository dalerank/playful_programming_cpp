# Регулярность

Представьте, что вам на исправление прилетает баг с приложенной записью игры. Сам игровой матч записан, но реплей воспроизводится нестабильно и юнит обходит угол слева, а QA пишет в отчёте, что очень редко бывает и справа, а потом игра вылетает по ассерту о неверной контрольной сумме. Состояние на входе побитово одинаковое, сид генератора один и тот же, бинарник один и тот же, и только на отдельных машинах получаются неправильные результаты. Причину такого бага можно искать очень долго, и похож сей увлекательный процесс на поиск иголки в стоге сена, особенно если её нет, а стог лежит на удалённой машине. Десинк нам уже встречался в главе про значения, только там расходились сами числа, а здесь... здесь ещё предстоит понять, в чём беда.

```cpp
struct Enemy { int id; int dmg; };

// Отсортировать цели по урону, а при равном уроне... а при равном уроне
// кто-то однажды дописал «ну хоть как-нибудь, лишь бы стабильно».
long long resolve_targets(vector<Enemy*>& v) {
    sort(v.begin(), v.end(), [](const Enemy* a, const Enemy* b) {
        if (a->dmg != b->dmg) return a->dmg > b->dmg;
        return a < b;                    // <- а вот тут сравниваются адреса
    });
    long long acc = 0;
    for (const Enemy* e : v) acc = acc * 31 + e->id;   // порядок важен
    return acc;
}
```

В процессе исследования этой ошибки мы и выходим на показанную выше функцию сортировки целей. Сортирует она и правда стабильно, но только в пределах одного запуска и если взять восемь врагов с одинаковым уроном и «собрать» их на двух «машинах» из одного и того же логического состояния, но выделить память в разном порядке, то получим одинаковые данные, одинаковый код и разный ответ, что-то вроде `116267632558` и `165191219038`. Стандарт, к слову, про `<` на указателях в несвязанные объекты ничего не обещает, определённый ответ тут даёт только `std::less`, так что эта сортировка уже спорная ещё до всякого десинка.

Разговор про равенство, копирование и математическую корректность легко принять за нужный одним любителям теории, а он весь про такие вот баги. К этому примеру мы вернёмся позже, а сейчас поговорим про регулярность и в чём её важность для разработчика.

## Что такое регулярный тип

Разговор про регулярность начать удобнее с обратного примера, с типа, который регулярным не является. Далеко ходить не надо, возьмём того же `Enemy` из начала главы и заглянем внутрь.

```cpp
/*
   Enemy, нерегулярный тип. У каждого врага свой лут, он живёт
   в куче, и Enemy держит на него сырой указатель.
   Копирование мелкое, а == сравнивает адрес лута: копия «равна»
   оригиналу, но не независима от него, лут у них один на двоих.
   Зато два врага с одинаковым содержимым карманов неравны.
*/
struct Loot { int gold; int ammo; };

class Enemy {
    Loot* loot_;
    int   id_;
public:
    // Конструктора по умолчанию нет, и std::default_initializable такой тип не пропустит.
    // Поля инициализируем строго в порядке объявления. Про нарушение
    // компилятор умеет предупредить (C5038), только предупреждение это
    // по умолчанию выключено и молчит даже на /W4, а на зависимых полях
    // перестановка дала бы уже чтение мусора.
    Enemy(int id, int gold)
        : loot_(new Loot{gold, 0}), id_(id) {}

    // Деструктора тоже нет, и тоже намеренно, с ним мелкая копия
    // отдала бы один и тот же Loot операционной системе дважды.

    // Копирующий конструктор копирует указатель, а не лут.
    // После этого copy.loot_ == orig.loot_, и обыск одного трупа
    // опустошает карманы другого. Это нарушение регулярности,
    // копия зависит от оригинала.
    Enemy(const Enemy& o)
        : loot_(o.loot_), id_(o.id_) {}       // <- намеренная ошибка

    // Оператор == сравнивает адреса, поэтому два врага с одинаковым
    // золотом и патронами считаются неравными. Это равенство по
    // идентичности указателя, а не по значению содержимого.
    bool operator==(const Enemy& o) const {
        return loot_ == o.loot_;              // <- намеренная ошибка
    }
};
```

Регулярный тип в современном понимании ведёт себя как value-типы вроде `int` (с оговорками для `double` и NaN/±0, см. главу про значения), предоставляя корректное равенство, копирование, присваивание и конструктор по умолчанию, причём копии независимы от оригинала. Ключевая аксиома в том, что если `a == b`, то после одной и той же регулярной операции результаты снова равны (`f(a) == f(b)`), и такая предсказуемость позволяет заменять равное на равное без потери смысла программы (конгруэнтность).

Теперь пробегитесь ещё раз глазами по `Enemy`, заметили, что конгруэнтность у него как раз держится? Равными два врага у такого `==` становятся, только когда один сделан копией другого, а копия тащит за собой и тот же `Loot`, и то же `id_`, трогать их снаружи нельзя и полей класс наружу не отдаёт, вот `f(a) == f(b)` и выходит само собой. Держится это на волоске, и стоит дописать конструктор `Enemy(int id, Loot* shared)`, как равными станут враги с разными номерами и конгруэнтность пропадёт.

Сломано в этом классе другое, потому что копии зависимы через указатель, и обыскав одну копию, вы обнуляете карманы у всех остальных. Обратный пример у нас тоже есть, это `Fixed` из прошлой главы, у которого всё состояние это одно 32-битное поле `raw`, и регулярным его сделала та единственная дописанная строчка с `<=>`, после которой он там звался `FixedOrdered`. На паре `Enemy` против `Fixed` удобно смотреть, чем одно отличается от другого.

## Откуда взялось само слово

Странно, вообще говоря, что для такой очевидной вещи понадобился отдельный термин, ведь пока вы пишете свой код, вы вряд ли задумываетесь о том, регулярны ли ваши классы. Вы написали `Enemy`, написали ему `==` и прекрасно знаете, что оператор делает внутри. Но всё это нужно тем, кто пишет код, который ваших типов в глаза не видел, а работать с ними обязан.

Родился термин не в `C++`, а в Ada, где уже с 1983 года были генерики, то есть можно было написать некую логику, работающую с любым типом элемента, и как только вы такое написали, вам нужно как-то объяснить, чего вы от чужого типа требуете. Не просто «он должен работать с этим генериком», а списком, копируется, сравнивается, копия независима, равные ведут себя одинаково. Этот список требований и есть регулярность.

> **1981.** Дипак Капур, Дэвид Массер и Александр Степанов, `Operators and Algebraic Structures`. Тип описывается не полями, а операциями и законами, которым эти операции подчиняются. До кода ещё далеко, это пока чистая алгебра.

> **1989.** Массер и Степанов, `The Ada Generic Library`. Здесь термин «регулярный тип» уже стоит в тексте рабочим понятием, и закрепляется он в языке с генериками, потому что там требования к чужому типу приходится выписывать явно.

> **1994.** Комитет голосует за включение STL в стандарт `C++`. Регулярность превращается из статьи в требование к вашим классам, только нигде не записанное, `std::sort` её ждёт, но сказать об этом не умеет.

> **2000.** Джеймс Денерт и Степанов, `Fundamentals of Generic Programming`. Регулярность разобрана по косточкам, включая ту её часть, которой в языке нет до сих пор.

> **2009.** Степанов и Пол Мак-Джонс, `Elements of Programming`. Книга, в которой из этих законов выводится половина стандартной библиотеки.

> **2020.** Концепт `std::regular` попадает в язык. Между тем, как термин закрепился, и тем, как компилятор научился его проверять, прошёл тридцать один год.

Тридцать один год эволюции, конечно, сложно уложить в один абзац, да это и не нужно, достаточно помнить, что именно приехало в язык в 2020 году. А приехала проверка, что у типа есть все нужные операции, а вот независимость копий и равенство по значению компилятору проверять нечем, для этого нужен математический аппарат совсем не того сорта, каким он пользуется сейчас.

## Регулярная функция

Регулярной может быть и функция, разговор про это шёл в главе про значения, где регулярность привычных операций над `double` ломали `NaN` и знак нуля. На допущении, что равные аргументы дают равные результаты, стоит вся алгоритмика стандартной библиотеки для типов-значений, от сортировки и поиска до преобразований последовательностей, отсюда и единый `std::sort` для `int`, `std::string` и ваших типов, а вот чего это допущение не даёт, видно на примере ниже.

```cpp
// Тот самый Fixed из прошлой главы, уже с дописанным <=>,
// значение в формате 16.16, всё состояние это одно 32-битное число.
struct Fixed {
    int32_t raw;
    auto operator<=>(const Fixed&) const = default;
};

template <typename T>
T midpoint_naive(T a, T b) {
    // Регулярность гарантирует, что равные входы дают равный результат,
    // но саму арифметику из воздуха не достаёт.
    return (a + b) / T(2);   // <- и вот здесь притаилось переполнение
}

template <class T>
concept has_plus = requires(const T& a, const T& b) { { a + b } -> same_as<T>; };

// Fixed регулярен по всем требованиям концепта...
static_assert(regular<Fixed>);
// ...но сложения у него нет, поэтому midpoint_naive<Fixed> не соберётся.
static_assert(!has_plus<Fixed>);
static_assert(has_plus<int>);
```

Слово «наивный» в имени я добавил неслучайно, и на `T = int` эта функция вычисляет отнюдь не середину. Возьмите `a = 2000000000` и `b = 2000000001`, что в сумме даст переполнение `int`, и вместо ожидаемых `2000000000` получится `-147483647`. На машине автора сборки `/Od` и `/O2` дают одинаковый результат, но полагаться на это нельзя, поскольку знаковое переполнение это неопределённое поведение, и другой компилятор с другими ключами вправе выдать что угодно.

Эта ошибка два десятилетия жила в бинарном поиске почти всех учебников, пока Джошуа Блох не написал о ней в 2006 году, и из-за неё в `C++20` завели `std::midpoint`, который считает середину так, чтобы промежуточный результат не выходил за диапазон типа. Как вы видите регулярность `int` тут ничем не помогла, да и помочь не могла, поскольку она обещает, что равные входы дадут равный выход, но не обещает, что выход будет правильным.

Заодно видно, чего регулярность не даёт. `Fixed` проходит `std::regular`, у него есть и равенство, и независимые копии, и конструктор по умолчанию, а `midpoint_naive<Fixed>` всё равно не соберётся, потому что складывать `Fixed` никто не научил. Регулярность отвечает за то, чтобы тип вёл себя как значение, а арифметику к этому значению приносите вы сами. И наоборот, у `Fixed` внутри тот же `int32_t`, так что стоит завести сложение в лоб, и переполнение приедет такое же.

## Сколько стоит равенство

Когда мы работаем со встроенными типами вроде `int` или `bool`, операции равенства, копирования и присваивания обычно считаем константными по времени, в одну-две машинные инструкции. У `double` сравнение тоже быстрое, но это уже не «просто биты», ведь `(+0.0 == -0.0) == true`, а `(NaN == NaN) == false`.

Работая со сложными типами, мы ожидаем, что проверка равенства займёт время, пропорциональное общему объёму данных. Ожидание разумное, но линейность тут не гарантирована ни сверху, ни снизу, и разброс получается существенный, возьмём две строки по мегабайту и замерим на машине автора, помня, что машина одна и у вас числа выйдут свои.


| что сравниваем               | время одного `==` |
| ---------------------------- | ----------------- |
| строки разной длины          | 1,1 нс            |
| отличаются в первом байте    | 4,8 нс            |
| отличаются в последнем байте | 39 мкс            |
| полностью равны              | 39 мкс            |


Между первой и последней строкой таблицы разница в тридцать пять тысяч раз, и обе строки про один и тот же `operator==`. Снизу линейность сбивает ранний выход и сравнение заканчивается на первом же символе, ещё раньше срабатывает проверка длины, поэтому строки разного размера отбраковываются вообще без чтения данных. Верхняя строка таблицы почти целиком состоит из накладных расходов самого замера, пустой цикл в той же обвязке даёт 0,5 нс.

Сверху линейность подпирает библиотека и для тривиально сравнимых типов в непрерывной памяти `std::equal` вправе свести почленный обход к одному вызову `memcmp`, а тот уже идёт векторными инструкциями и обработает мегабайт за сорок микросекунд. Т.е. стоимость сравнения зависит от данных сильнее, чем от типа и если ваш профайлер показывает копейки на синтетике, то на боевых данных он может показать совершенно другое.

А бывает, что дорожает само понятие равенства, и сравнение байтов будет ни при чём. Возьмите мультимножество, неупорядоченную коллекцию элементов с возможными повторениями, скажем инвентарь игрока, три зелья, два ключа и меч, сложенные в `std::vector` в том порядке, в каком их подобрали. Два таких инвентаря равны, когда в них лежит одно и то же, а порядок подбора никого не волнует, и чтобы это проверить, нужно либо отсортировать оба и сравнить лексикографически, что даст O(n log n), либо для каждого элемента первого проверить его наличие во втором с учётом кратности, что даст O(n²). Данных там всё те же n штук, а цена сравнения выросла, потому что «равны» тут значит «те же элементы в любом порядке».

## Когда равенство слишком дорого

В некоторых случаях равенство по смыслу может оказаться вычислительно тяжёлым настолько, что от него отказываются и ищут другие способы сравнить значения. Хрестоматийный пример тут будет проверка изоморфизма графов. Граф A и граф B выглядят по-разному, разные имена вершин, разное расположение на схеме, но если переименовать `0→A, 1→C, 2→B, 3→D`, все рёбра совпадут один к одному, а значит, графы изоморфны, это одна и та же структура, просто нарисованная иначе.

```text
       Граф A                        Граф B

          0                             A
         / \                           / \
        /   \                         /   \
       1-----2                       B-----C
       |                                   |
       3                                   D

   рёбра  0-1  0-2  1-2  1-3     рёбра  A-B  A-C  B-C  C-D

               изоморфизм:   0→A   1→C   2→B   3→D
```

Напрашивающееся соответствие «по позиции на схеме», где `1→B` и `2→C`, не работает, потому что у вершины `1` три соседа, а у `B` только два, и висячее ребро `1-3` просто некуда деть. Единственная зацепка, за которую тут можно ухватиться глазами, это степени вершин, и то она лишь отсеивает заведомо неподходящие варианты, а не находит нужный.

Проверить изоморфизм в лоб значит перебрать все способы переименовать вершины одного графа в вершины другого, а это `n!` вариантов и уже при `n = 20` их 2 432 902 008 176 640 000, то есть два с половиной квинтиллиона, так что перебор отпадает сразу. Быстрого алгоритма для этой задачи никто не нашёл, но и доказать, что его не существует, тоже пока ещё никто не смог. Дальше всех среди «быстрых решений» продвинулся Ласло Бабаи в 2015 году, и его алгоритм несравнимо быстрее перебора, хотя до по-настоящему быстрого всё равно не дотягивает.

Впрочем, на практике всё не так мрачно и существующие солверы вроде `nauty` и `VF2` справляются с графами на тысячи вершин мгновенно, потому что живые графы почти никогда не оказываются тем самым худшим случаем. Но и гарантии, что вам не попадётся именно такой случай, у вас всё же нет.

В таких ситуациях программист вынужден либо отказаться от полноценного равенства по смыслу, либо ограничиться представительным равенством и сравнивать биты напрямую, то есть считать два значения равными, если их битовый образ идентичен. Для составных объектов это часто рекурсивное сравнение полей, но сырой `memcmp` по всей структуре опасен, если в ней есть «дырки» (паддинг), и одинаковый смысл при разном мусоре в «дырках» даст ложный результат при равных значениях. И наоборот, `memcmp` не стоит принимать за осмысленный `operator==`, даже когда он случайно даёт правильные ответы.

## Структурный порядок вместо смыслового

Та же история с порядком и когда истинный порядок «по смыслу» недоступен или слишком дорог, то берут лексикографический или по первым отличающимся полям, и обычно этого хватает, чтобы сортировать и искать.

```cpp
/*
   Структурный порядок вместо смыслового
   Когда истинный порядок «по смыслу» недоступен или дорог,
   лексикографический / по полям это практичная альтернатива.
   std::sort, std::map, std::lower_bound работают с любым
   строгим слабым порядком, не требуя «правильного» смысла.
*/

struct Fixed {
    int32_t raw;

    // Структурный порядок по единственному полю. Он же оказывается
    // и смысловым, потому что raw растёт вместе со значением, и это
    // тот редкий случай, когда одно совпало с другим бесплатно.
    //
    // Отдельный operator== писать не нужно: дефолтный <=> объявляет
    // дефолтный == сам, из == выводится !=, а из <=> выводятся
    // <, >, <= и >=. Шесть операторов из одной строки.
    auto operator<=>(const Fixed&) const = default;
};

struct ReplayHeader {
    std::string map;
    int         tick;
    std::string winner;

    // А тут порядок чисто структурный: map → tick → winner.
    // Смыслового порядка у записей матча нет, никто не скажет,
    // какой реплей «больше», но для std::set и std::map хватает.
    auto operator<=>(const ReplayHeader&) const = default;
};

// Проверяем, что шесть операторов действительно появились.
// В формате 16.16 единица это 65536, половина 32768, полтора 98304.
static_assert(Fixed{65536} == Fixed{65536});
static_assert(Fixed{65536} != Fixed{32768});
static_assert(Fixed{32768} <  Fixed{65536});
static_assert(Fixed{98304} >= Fixed{65536});
```

Однако не все объекты вообще допускают копирование или равенство, и если объект владеет уникальным ресурсом вроде открытого файла, сетевого соединения или GPU-буфера, то ни копирование, ни присваивание к нему смысла не имеют, и такие типы мы зовём «естественно нерегулярными», а правила обращения с ними приходится проговаривать словами, потому что из сигнатур они не читаются.

## Буква и смысл

В современном `C++` часть идей регулярности получила языковое выражение в концептах. Концепты фиксируют синтаксический контракт, то есть что тип умеет копироваться и сравниваться, и контракт этот довольно близок к идее, которую Степанов описал ещё в восьмидесятые. Вот только между «умеет» и «делает это осмысленно» лежит пропасть.

Лучше всего она видна, если прогнать через концепты обоих героев главы вместе со стандартными типами. `Fixed` проходит проверку и по букве, и по смыслу, а `Enemy` заваливает `std::regular`, ведь у него нет конструктора по умолчанию, и это единственное, что заметил компилятор. Настоящая же беда `Enemy` в том, что его `operator==` врёт и про это вам ни один концепт не скажет. Допишите `Enemy` конструктор по умолчанию, и `std::regular<Enemy>` станет истинным, хотя равенство как сравнивало адреса, так и будет сравнивать. Т.е. мы вполне можем написать тип, который пройдёт все проверки концепта, но при этом будет вести себя некорректно.

`std::optional` при регулярном `T` хорошо ложится на value-семантику, равенство и копирование у него про значение, а вот на `std::string_view` удобно показать, чем буква отличается от смысла. Формально `std::regular<std::string_view>` истинно, тип копируется, конструируется по умолчанию, сравнивается на равенство, все требования выполнены. Но по смыслу копия дублирует только указатель и длину, а данные под ним остаются общими. С `std::span` комитет пошёл дальше и сравнение у него отобрал, операторы хоть и были в черновиках, но их убрали перед выпуском `C++20`, так что `std::span` не то что нерегулярный, он даже не `equality_comparable`, и попытка написать `a == b` для двух `span` не соберётся.

```cpp
// Концепт отвечает на вопрос «синтаксис на месте?»,
// а вовсе не на вопрос «смысл правильный?».
template <class T>
concept has_eq = requires(const T& a, const T& b) {
    { a == b } -> convertible_to<bool>;
};

struct Fixed {                               // герой главы
    int32_t raw;
    auto operator<=>(const Fixed&) const = default;
};

struct Loot { int gold; int ammo; };

class Enemy {                                // и злодей
    Loot* loot_;
    int   id_;
public:
    Enemy(int id, int gold) : loot_(new Loot{gold, 0}), id_(id) {}
    bool operator==(const Enemy& o) const { return loot_ == o.loot_; }
};

static_assert(regular<Fixed>);               // и по букве, и по смыслу
static_assert(regular<string>);              // и по букве, и по смыслу
static_assert(regular<string_view>);         // по букве да, по смыслу нет
static_assert(regular<optional<int>>);       // если регулярен сам T

static_assert(!regular<Enemy>);              // конструктора по умолчанию нет
static_assert(has_eq<Enemy>);                // а сравнение есть, только лживое

static_assert(!regular<span<int>>);          // сравнения нет вовсе
static_assert(!has_eq<span<int>>);           // a == b не соберётся
static_assert(copyable<span<int>>);          // копируется

static_assert(!regular<unique_ptr<int>>);    // не копируется
static_assert(has_eq<unique_ptr<int>>);      // зато сравнивается
```

Оптимизатор про `std::regular` не знает ничего и никаких выводов из концепта не делает. Замена равного на равное и кэширование результатов это правила, по которым рассуждаете вы, а компилятор имеет свои, самостоятельно доказывая отсутствие побочных эффектов, и на объявленный концепт ему при этом наплевать. Тем более он не выводит алгебраические свойства вроде коммутативности (`a + b` против `b + a`), которую `std::regular` не обещает и обещать не может. Написать `template<std::regular T> void process(T value);` вы можете уже сегодня, и компилятор проверит синтаксические требования концепта, то есть копируемость, сравнимость на равенство и прочее в том же духе, а равенство по значению и независимость копий по-прежнему остаются на авторе типа.

## Как починить `Enemy`

Попробуем починить главного «злодея» главы, чтобы он правильно работал с алгоритмами стандартной библиотеки, и для этого перестанем прятать состояние за указателем.

```cpp
struct Loot {
    int gold;
    int ammo;
    auto operator<=>(const Loot&) const = default;
};

struct Enemy {
    int  id;
    int  dmg;
    Loot loot;                     // лут внутри, а не за указателем

    // Копирование, присваивание и конструктор по умолчанию компилятор
    // напишет сам и напишет правильно, потому что все поля уже ведут
    // себя как значения. Сравнение тоже, и тоже одной строкой.
    auto operator<=>(const Enemy&) const = default;
};

// Та самая проверка, которая на прошлом Enemy падала.
static_assert(regular<Enemy>);
static_assert(totally_ordered<Enemy>);

// Равенство теперь про содержимое, а не про адреса.
static_assert(Enemy{7, 40, {100, 30}} == Enemy{7, 40, {100, 30}});
static_assert(Enemy{7, 40, {100, 30}} != Enemy{7, 40, {100, 29}});

// И тот самый сортировщик целей из начала главы. Сортируем значения,
// а не указатели, поэтому добивать сравнение адресами больше негде.
long long resolve_targets(vector<Enemy>& v) {
    sort(v.begin(), v.end(), [](const Enemy& a, const Enemy& b) {
        if (a.dmg != b.dmg) return a.dmg > b.dmg;
        return a.id < b.id;        // <- значение, а не адрес
    });
    long long acc = 0;
    for (const Enemy& e : v) acc = acc * 31 + e.id;   // та же свёртка
    return acc;
}
```

Обратите внимание, что руками тут почти ничего не написано. Ни копирующего конструктора, ни присваивания, ни `==`, ни четырёх операторов сравнения и всё это компилятор сгенерировал сам и сгенерировал верно, потому что каждое поле теперь ведёт себя как значение, `int` ведёт, `Loot` ведёт, значит и `Enemy` тоже ведёт. Регулярность собирается снизу вверх, и это, пожалуй, самое приятное её свойство, соберите тип из значений, и он получит поведение значения бесплатно.

Обыск копии больше не трогает оригинал, у него по-прежнему останется сто золота, и две «машины», собравшие восьмерых врагов из одного логического состояния в разном порядке выделения памяти, теперь дают одну и ту же свёртку, `947656708` и `947656708`, вместо разъехавшихся `116267632558` и `165191219038`. Десинка нет, и убрали мы его тем, что из симуляции пропали адреса, на которые можно было опереться, никакого хитрого сравнения на равных для этого не понадобилось.

Может оказаться, что `Enemy` вам вообще не нужен как значение. Если враг это сущность на поле боя, со своей личностью и своим временем жизни, то два врага с одинаковым золотом и патронами вовсе не «равны», они просто похожи, и правильный ответ тогда просто не писать `==` вовсе. Регулярность нужна значениям, урону, координате, `Fixed`, строке в таблице результатов. Беда прошлой версии `Enemy` в том, что нерегулярному по смыслу типу мы хотели навесить поведение значения. Он копировался, сравнивался, выглядел как значение, а значением не был, и ошибки от этого вылезали то в одном месте, то в другом.

## Что из этого следует для ваших типов

**Равенство считайте только по значению.** Ни адрес, ни `capacity`, ни время создания, ни номер ячейки в `==` попадать не должны. Всё, что вы туда пустите, придётся потом тащить за собой в порядок и в хеш, иначе они разойдутся с равенством и контейнеры начнут терять ваши объекты.

**Компаратор должен быть строгим.** Для равных элементов он обязан вернуть `false`, то есть `<`, а не `<=`. Отладочная сборка MSVC ещё ловит нарушение проверкой `invalid comparator`, а релизная промолчит и, скорее всего, баг уедет в прод к игрокам.

**Копия обязана быть независимой.** Если после копирования правка одного объекта видна в другом, у вас не тип-значение, а два имени для одной вещи.

**Порядок обхода не должен зависеть от адресов.** Сортировка по указателю не воспроизводится между запусками, и `unordered_map` с ключами-указателями тоже, три запуска одного бинарника дали у автора три разных порядка обхода. А вот с ключами-значениями, `int` или `string`, обход как раз стабилен от запуска к запуску.

`std::regular` **проверяет синтаксис, а не смысл.** Галочка от компилятора не поможет избежать ошибок, если вы не продумали свой тип.

Регулярность типа это право заменить равное на равное, а красота и галочка от концепта тут ни при чём. Пока вы это гарантируете, `std::sort` будет правильно сортировать, `unordered_map` находить, и реплей на двух машинах воспроизводиться одинаково. Как только регулярность теряется, вместе с ней пропадает и возможность рассуждать о корректности написанного кода, и остаются только баги.
