# Вычислительная база

Большинство команд, которые делают мультиплеерные стратегии, рано или поздно сталкиваются с ошибками детерминизма симуляции, когда требуется, чтобы все клиенты получили не «примерно то же», а бит в бит одинаковый результат. С `float` этого сделать не всегда возможно из-за невоспроизводимости отдельных операций, и сложение, умножение, деление, а также корень стандарт IEEE 754 требует округлять точно, и они как раз повторяемы, а вот `sin`, `cos` и `exp` и ещё куча других алгоритмов и функций не стандартизованы, так что на разных библиотеках, версиях компилятора и даже флагах вроде `/fp:fast` они могут давать разные младшие биты. Поэтому командам приходится писать свой тип с фиксированной точкой, свои операции, свои синусы и корни. Некоторые операции можно получить бесплатно (сложение и сравнение), при работе с другими приходится подумать над реализацией, или сделать «в лоб», обманувшись лёгкостью наивной реализации.

```cpp
// 16.16, детерминированная арифметика для реплеев
struct Fixed {
    int32_t raw;
};

// деление в лоб: вычитаем делитель, пока есть что вычитать
// (и это ещё только для положительных, с отрицательными всё веселее)
Fixed divide(Fixed a, Fixed b) {
    int64_t rem = (int64_t)a.raw << 16;
    int64_t d = b.raw;
    int32_t q = 0;
    while (rem >= d) {
        rem -= d;
        ++q;
    }
    return Fixed{q};
}
```

Это будет работать, и работать правильно, пока в один из дней вы не заметите, что на пятистах снарядах профилировщик показывает в горячих функциях этот `divide`, потому что, повторив простую модель деления образца 1952 года, вы выбрали очень дорогой способ. То, какие операции считать основными, а какие производными, и называется вычислительной базой, и ниже мы посмотрим, как архитекторы процессоров делали это последние восемьдесят лет и как её следует выбирать вам, когда станете писать свой `Fixed`, `BigInt` или `Vec3`.

Чтобы выполнять действия над типом, надо понимать, какие операции ваш тип вообще поддерживает. Для любого типа значений можно задать некоторый минимальный набор процедур, из которых можно построить все остальные операции над ним, и такой набор называют вычислительной базой типа. Например, для беззнаковых `k`-битных целых можно взять операции «получить ноль», «проверить равенство» и «перейти к следующему значению», и теоретически из них можно реализовать и сложение, и умножение, и сравнение, просто как очень длинные последовательности вызовов «следующего» и проверок.

## Почему трёх операций мало

Здесь вступает в игру понятие эффективности и базу называют более эффективной, если типичные процедуры над типом получаются на ней не хуже по порядку стоимости, чем на другой разумной базе с более «прямыми» примитивами. В примере ниже с одним только `next` всё плохо и сложение двух `k`-битных чисел через многократный инкремент будет в худшем случае занимать порядка `2^k` шагов, тогда как аппаратный `ADD` для фиксированной ширины обычно константен по значениям аргументов, потому что число тактов задаёт микроархитектура, а не величина слагаемых. Посмотрим на эту базу целиком.

```cpp
// ---- минимальная база: теоретически достаточная ----
namespace MinimalBase {
    using uint = unsigned int;

    // три примитива
    uint zero() { return 0; }
    bool equal(uint a, uint b) { return a == b; }
    uint next(uint a) { return a + 1; }

    // сложение через многократный инкремент: O(b) шагов
    uint add(uint a, uint b) {
        uint result = a;
        for (uint i = zero(); !equal(i, b); i = next(i))
            result = next(result);
        return result;
    }

    // умножение через многократное сложение: O(a*b) шагов
    uint multiply(uint a, uint b) {
        uint result = zero();
        for (uint i = zero(); !equal(i, a); i = next(i))
            result = add(result, b);
        return result;
    }

    // сравнение: a < b, если поднимаясь от нуля к b, мы встречаем a раньше,
    // чем упираемся в b. O(b) вызовов next, без prev и без вычитания
    bool less(uint a, uint b) {
        for (uint i = zero(); !equal(i, b); i = next(i))
            if (equal(i, a))
                return true;
        return false;
    }
}

int main() {
    assert(MinimalBase::add(2, 3) == 5);
    assert(MinimalBase::multiply(4, 5) == 20);
    assert(MinimalBase::less(3, 7));
    assert(!MinimalBase::less(7, 3));
}
```

Слово «неэффективно» такая база подтверждает достаточно быстро, и `multiply(1000, 2000)` даст два миллиона вызовов `next`, и один такой вызов в дебаге занимает 5,5 миллисекунды, так что ни о каком реальном применении, когда умножение съедает треть кадра, речи не идёт. Аппаратное умножение в том же прогоне обходится в 0,5 наносекунды, и это отношение примерно в десять миллионов раз.

Но если собрать программу с оптимизациями, то он уложится в 0,4 микросекунды, потому что оптимизатор видит во внутреннем цикле инкрементов обычное сложение и сворачивает его, оставляя от двух миллионов шагов тысячу итераций внешнего цикла. Соблазнительно на этом успокоиться, но получилось это только из-за простого типа данных `unsigned`, операции с которым видны компилятору целиком. Как только вместо `unsigned` окажется что-то нетривиальное с проверкой диапазона, состоянием или обращением к таблице, сворачивать станет нечего, и вы опять получите миллисекунды. Тем наивная база и опасна, что на игрушечном типе её проблемы спрячет оптимизатор, а на реальном спрятать уже не получится.

## Почему семи операций тоже мало

Но даже если ваша вычислительная база эффективна, то этого тоже мало, и второй важной характеристикой базы является её выразительность. База называется выразительной, если с её помощью удобно и компактно определять процедуры над типом, которые регулярно встречаются в практике. Можно, конечно, сказать, что вычитание двух произвольных чисел это излишество, ведь его выражают через прибавление противоположного, а для беззнаковых противоположного просто нет. Но если вы попытаетесь писать реальный код только с операциями `+`, `0` и `next`, то обнаружите, что многие определения просто становятся громоздкими и нечитаемыми, поэтому, когда мы проектируем выразительность базы, мы добавляем в неё операции, которые логически выводимы из других, но практическая польза от их явного наличия гораздо выше, чем цена увеличения базы.


| База          | Что добавили                                                           | Чем платим и что получаем                                                                                                  |
| ------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| минимальная   | `zero`, `equal`, `next`                                                | выразить можно всё, но сложение линейно по значению, а умножение квадратично                                               |
| эффективная   | `add`, `subtract`, `multiply`, `less`                                  | стоимость операций перестала зависеть от значений аргументов, зато примитивов стало вдвое больше                           |
| выразительная | `not_equal`, `less_equal`, `greater`, `divide`, `modulo`, `min`, `max` | ничего нового не вычисляется, но код становится более понятным, а в `C++20` вся группа сравнений выводится из одного `<=>` |


Последний уровень легко принять за косметику, но такая косметика повышает уже человеческую «эффективность». Возьмём `Fixed` из начала главы, у которого сравнений нет, и его же с одной добавленной строчкой.

```cpp
struct Fixed {                        // тот самый тип из начала главы
    int32_t raw;
};

bool less_raw(Fixed a, Fixed b) { return a.raw < b.raw; }

struct FixedOrdered {                 // он же плюс одна строчка
    int32_t raw;
    auto operator<=>(const FixedOrdered &) const = default;
};

static_assert(!std::totally_ordered<Fixed>);
static_assert(std::totally_ordered<FixedOrdered>);

void sort_bare(std::vector<Fixed> &v) {
    std::sort(v.begin(), v.end(),
              [](Fixed a, Fixed b) { return less_raw(a, b); });   // лямбда в каждом вызове
}

void sort_ordered(std::vector<FixedOrdered> &v) {
    std::sort(v.begin(), v.end());                            // лучше
}
```

С первым вариантом не работает ни `std::clamp`, ни `std::min`, ни `std::set`, а каждый вызов алгоритма приходится сопровождать лямбдой, которую легко можно написать по-разному и получить сортировку, не согласованную с поиском. Со вторым всё это доступно сразу, можно проверить концептом, а не обещать в комментариях, и выразительность, получается, уже про то, как ваш тип будет взаимодействовать со стандартной библиотекой и чужим кодом. Так вышло со стандартом `C++` и язык формально можно было сделать минималистичным с операторами вроде `-`, `*`, `/`, проверки `<` и `>`, и долгое время комитет не решался вводить новые операции, чтобы сохранить совместимость. Но настало время и в `C++20` пришлось проделать работу по улучшению выразительности, и вместо шести операций сравнения ввели в базу одну, трёхстороннее сравнение `<=>`, из которой выводятся `<`, `>`, `<=` и `>=`, а `==` стандарт объявляет рядом автоматически. Теперь достаточно написать один примитив вместо шести производных, и забыть про добрую половину ошибок, когда кто-то забывал согласовать `<` с `==`.

## Как база росла в железе

### 1940-е и 1950-е: минимальная база

ENIAC (1945) не имел хранимой программы и «инструкции» задавались коммутационными панелями, а базовая арифметика шла через десятичные кольцевые счётчики-аккумуляторы. Под умножение и деление с извлечением корня в машине стояли отдельные блоки, то есть даже там, где программы ещё не было, дорогие операции уже спрятали в железо. Первой машиной с хранимой программой стал манчестерский Baby (1948) и база у него была очень скромная, всего семь инструкций, а из арифметики было только вычитание, а сложение программисту приходилось собирать самому, а выглядело это примерно вот так.

```cpp
// у Baby из арифметики было только вычитание
unsigned int add_via_sub(unsigned int a, unsigned int b) {
    return a - (0u - b);   // те же a + b
}
```

EDSAC (1949) и Manchester Mark 1 (1949) уже умели аппаратно умножать. IBM 701 (1952), первый коммерческий научный компьютер IBM с аппаратным умножением и делением, занимавшими десятки машинных тактов. На фоне сложения за считанные такты это всё равно выглядело как сильное расширение вычислительной базы, деление же реализовывали методом последовательных вычитаний, только со сдвигом на каждом разряде, а не по единице, как в примере из начала главы.

### Конец 1950-х и 1960-е: плавающая точка и режимы адресации

IBM 704 (1954), первый массовый компьютер с аппаратной плавающей точкой и индексными регистрами, которые позволили адресовать массивы циклом, а не подставлять адрес вручную. Выяснилось, что если в базе нет индексной адресации, то взять `a[i]` не получится, и можно только вписать адрес в саму инструкцию, то есть программы того времени на ходу меняли собственный код.

```text
; условный ассемблер, машина без индексных регистров
      LOAD  BASE       ; адрес начала массива
      ADD   I          ; прибавили номер элемента
      STORE NEXT+1     ; вписали сумму в адресную часть следующей команды
NEXT: LOAD  0          ; этот ноль только что переписали, тут и будет a[i]

; та же выборка на машине с индексным регистром
      LXA   I, 1       ; номер элемента в индексный регистр 1
      CLA   BASE, 1    ; взяли a[i], сама инструкция не менялась
```

В случае с индексным регистром ваш код остаётся неизменным и его становится возможно положить в постоянную память или разделить между процессами. Сегодня от всей этой истории осталось `a[i]`, за которым скрывается одна аппаратная инструкция с адресацией по базе и индексу.

> IBM System/360 (1964) принесла унификацию линейки и одну систему команд для машин от небольших до мейнфреймов. Больше ста опкодов, адресация вида `base + index + displacement`.

> PDP-8 (1965) обходилась восемью инструкциями, а скудость набора компенсировала косвенной адресацией и автоинкрементными ячейками, показав, что маленькая база с умными режимами адресации даёт гибкость не хуже большой.

> CDC 6600 (1964), первый успешный суперкомпьютер, где десять функциональных устройств работали параллельно, а порядок инструкций раскладывал скорборд (настоящая конвейеризация пришла позже, в 7600). Компилятор Fortran для него уже занимался планированием порядка инструкций, чтобы устройства не простаивали.



### 1970-е: микропроцессоры, x86, сопроцессоры

> Intel 4004 (1971), 4-битный, порядка четырёх десятков инструкций, умножения нет. Минимальная база в кремниевом чипе.

> Intel 8080 (1974), 8 бит, появилась инструкция `DAA` для десятичной арифметики, то есть сложение десятичных цифр в двоичном регистре. Пример расширения базы под конкретную прикладную область, бухгалтерию и кассовые аппараты, а парная ей `DAS` для вычитания доехала только с 8086.

> Zilog Z80 (1976) добавил `LDIR` (block move) и `DJNZ` (decrement and jump if non-zero), то есть аппаратную реализацию паттерна «счётный цикл», ещё один пример того, как частый программный приём спускается в железо.

Intel 8086 (1978), 16 бит, 16-битное умножение `MUL` и `IMUL`, деление `DIV`, и операции `MOVS`, `LODS`, `STOS`, которые вместе с префиксом `REP` давали аппаратный цикл копирования памяти, и если раньше требовался явный цикл на ассемблере, то сейчас это стало одной инструкцией.

```cpp
void copy_by_hand(char *dst, const char *src, std::size_t n) {
    for (std::size_t i = 0; i < n; i++)
        dst[i] = src[i];
}

void copy_today(char *dst, const char *src, std::size_t n) {
    std::memcpy(dst, src, n);
}
```

На 64 мегабайтах побайтовый цикл занимает от восьми до одиннадцати миллисекунд, а `memcpy` укладывается в две с половиной, потому что `memcpy` копирует по тридцать два байта векторными регистрами и заодно умеет обходить кэш на больших блоках.

> Intel 8087 (1980, формально уже переход в 1980-е) добавил сопроцессор с 80-битным стеком регистров и инструкциями вроде `FSQRT`, `FPTAN`, `FPATAN`, `FYL2X`, `F2XM1`. Тяжёлая вещественная арифметика и часть трансцендентных функций ушла из длинных библиотечных циклов в кремний, но отдельные `FSIN` и `FCOS` появились позже, примерно с 387, и компиляторы стали предпочитать аппаратные опкоды библиотечному `sin`, когда цель их поддерживала.



### 1980-е: RISC и философия «компилятор умнее микрокода»

Беркли RISC (1980) и Стэнфорд MIPS (1981), академические проекты, показавшие, что простые инструкции фиксированной длины позволяют сделать длинный конвейер без простоев, а сложные операции выгоднее реализовывать в компиляторе, чем в микрокоде.

> Intel 80186 (1982) забрал в железо пролог и эпилог функции с `PUSHA` и `POPA`, которые сохраняют все регистры одной инструкцией, а `ENTER` и `LEAVE` строят и разбирают кадр. Из этой пары выжила только `LEAVE`, о чём мы уже говорили в главе про процедуры. Intel 80386 (1985) добавил к этому 32 бита и 32-битные формы тех же инструкций.

ARM (1985, Acorn), трёхадресная RISC-система команд с условным исполнением (предикацией) многих инструкций, когда компилятор мог свернуть короткие ветки `if` в линейный код без прыжков. Со спекулятивным исполнением это ничего общего не имеет, приём просто про то, чтобы меньше прыгать, и на процессорах со слабым предсказателем переходов он оказался очень хорош. Проще всего это видно на одной строчке `if (x != 0) y = 1;`, которая превращается либо в ветку, либо в предикацию.

```text
; обычный путь, с прыжком
      CMP   r0, #0
      BEQ   skip
      MOV   r1, #1
skip:

; то же самое предикацией, прыжка нет вообще
      CMP   r0, #0
      MOVNE r1, #1     ; инструкция выполнится, только если не равно
```

Позже в 64-битном ARM от него отказались, оставив условную пересылку `CSEL` и пару родственных инструкций. Причина в самой предикации, которая занимает биты в каждой инструкции и усложняет конвейер, а выигрыш даёт только на коротких ветках, так что при переходе на широкие суперскалярные ядра плата за неё перестала оправдываться.

> MIPS R2000 (1985) получил отдельный блок умножения и деления, который работал асинхронно от конвейера, так что результат забирали из отдельных регистров, когда он был готов.

> SPARC (1987, Sun) появилась позже первых коммерческих RISC (MIPS R2000 и PA-RISC были раньше), зато принесла регистровые окна, когда при вызове функции окно сдвигается, и аргументы с локальными переменными попадают в другие регистры, а сохранять их в память не нужно вовсе. Это редкий случай, когда в базу опустили не арифметику, а само соглашение о вызовах.



### 1990-е: SIMD и расширение базы «в ширину»

> Intel MMX (1996, Pentium MMX) добавил пятьдесят семь новых инструкций и восемь 64-битных регистров с `mm0` по `mm7`, а одна `PADDB` складывала сразу восемь пар байт. Регистры при этом были наложены на регистры x87, поэтому смешивать вещественную арифметику и SIMD в одной функции стало отдельным искусством. Видеокодеки, звук и 2D-графика быстро подхватили SIMD, и на удачных алгоритмах ускорение бывало кратным, но «в N раз» всегда зависело от задачи, данных и того, переписали ли горячий путь вручную.

> AMD 3DNow! (1998, K6-2) добавил набор инструкций для пары `float32` и был нацелен на геометрию 3D-игр с инструкциями вроде `PFMUL`, `PFADD`, `PFRCPIT1`. Нишевое расширение базы под один конкретный рынок, дальше него оно и не ушло.

> Intel SSE (1999, Pentium III) добавил ещё один крупный пласт SIMD-команд и восемь новых 128-битных регистров с `xmm0` по `xmm7`. Флаг `-msse` в GCC открыл к ним доступ, а вот автоматическая векторизация появилась там заметно позже, только в GCC 4.0 (2005), так что первые годы SIMD оставался ручной работой.

SSE2 (2001, Pentium 4) добавил двойную точность и целочисленный SIMD в `xmm`-регистрах, после чего компиляторы начали быстро переходить на SSE2 и для обычной скалярной плавающей точки. Как выглядело расширение базы «в ширину» на практике, проще показать на сложении двух массивов. Сначала обычный цикл, потом он же через SSE, по четыре числа за итерацию.

```cpp
void add_scalar(float *dst, const float *a, const float *b, std::size_t n) {
    for (std::size_t i = 0; i < n; i++)
        dst[i] = a[i] + b[i];
}

// n кратно четырём
void add_sse(float *dst, const float *a, const float *b, std::size_t n) {
    for (std::size_t i = 0; i < n; i += 4) {
        __m128 va = _mm_loadu_ps(a + i);
        __m128 vb = _mm_loadu_ps(b + i);
        _mm_storeu_ps(dst + i, _mm_add_ps(va, vb));
    }
}
```

Замер на массиве, который целиком лежит в кэше, даёт следующую картину. Если запретить компилятору векторизовать первый цикл, он занимает 780 миллисекунд и рукописный SSE даёт почти двукратный прирост, занимая 452 мс. А отданный автовекторизатору будет занимать 265 миллисекунд, обгоняя рукописную версию почти вдвое. (Цифры взяты для примера с моего ноутбука) Ничего мистического здесь нет и компилятор не обязан держаться за 128 бит, которые были написаны руками, и он берёт регистры пошире, попутно ещё и разворачивая цикл. В 1999 году такой роскоши не было и весь SIMD-код писали руками, а сегодня рукописные интринсики оправданы только там, где автовекторизатор не справляется и нужно вмешательство разработчика.

> x86-64 или AMD64 (2003, AMD Opteron) технически относится к двухтысячным, но корнями уходит в девяностые, проект начался около 1999 года. Теперь регистры были расширены до 64 бит, добавлены регистры с `r8` по `r15`, а SSE2 стал обязательной частью базы.



### 2000-е: 64 бита повсюду, криптография, строки

> SSE3 (2004, Prescott) добавил горизонтальное сложение `HADDPS`, складывающее соседние дорожки внутри регистра, и понадобилось оно комплексной арифметике и свёрткам, так что и здесь код под давлением рынка переехал в кремний.

> SSSE3 (2006, Core 2) принёс `PSHUFB`, перестановку байт по маске, ставшую одним из самых мощных примитивов, через который делают таблицы подстановки и битовые манипуляции без ветвлений.

SSE4.1 и 4.2 (2007 и 2008) добавили `PMULDQ` (умножение 32 на 32 с результатом в 64 бита), `PCMPESTRM` для поиска в строке и `CRC32`, и теперь строковые алгоритмы и хеш-функции получили аппаратную поддержку. Алгоритм `CRC32` будет тут, пожалуй самым показательным, поскольку до этого контрольную сумму считали по таблицам, и таскали их из проекта в проект.

```cpp
extern uint32_t table[256];   // та самая таблица, 1 КБ данных

uint32_t crc32c_table(const uint8_t *p, std::size_t n) {
    uint32_t c = 0xFFFFFFFFu;
    for (std::size_t i = 0; i < n; i++)
        c = table[(c ^ p[i]) & 0xFF] ^ (c >> 8);
    return c ^ 0xFFFFFFFFu;
}

uint32_t crc32c_hw(const uint8_t *p, std::size_t n) {
    uint32_t c = 0xFFFFFFFFu;
    std::size_t i = 0;
    for (; i + 8 <= n; i += 8)
        c = (uint32_t)_mm_crc32_u64(c, *(const uint64_t *)(p + i));
    for (; i < n; i++)
        c = _mm_crc32_u8(c, p[i]);
    return c ^ 0xFFFFFFFFu;
}
```

На шестнадцати мегабайтах табличная версия занимает около 28 миллисекунд, аппаратная около 1,5, разница примерно в двадцать раз, и таблица больше не занимает кэш данных. Но тут тоже есть подвох, и аппаратная инструкция считает не тот `CRC32`, что лежит в zip и zlib, а используется вариант Кастаньоли с другим порождающим полиномом, который называют `CRC-32C`. Суммы у них не совпадают, так что заменить одно другим в существующем формате файла не получится, и это тоже хороший пример того, что в базу могут опустить не саму операцию, а какую-то одну конкретную её версию.

### 2010-е: AVX, битовая алгебра, транзакционная память

> AVX (2011, Sandy Bridge) добавил 256-битные регистры `ymm`, то есть восемь чисел `float32` или четыре `float64` в одном регистре, и заодно избавился от разрушающих операций, так что результат теперь пишется в отдельный регистр, а не затирает первый аргумент.

> AVX2 (2013, Haswell) довёл до 256 бит и целочисленный SIMD, и GCC с `-march=haswell` начал автоматически векторизовать заметно больше паттернов.

`POPCNT` (SSE4.2 и ABM, около 2008) считает число единичных бит за одну инструкцию. В играх такой код встречается часто, будь то маска занятых клеток, маска живых юнитов в отряде или битовые множества видимости. До 2008 года его писали двумя способами, в лоб или трюком с масками, а с `C++20` для этого есть `std::popcount` из `<bit>`.

```cpp
// в лоб: тридцать два прохода по битам
int popcount_naive(uint32_t x) {
    int n = 0;
    for (int i = 0; i < 32; i++)
        n += (x >> i) & 1u;
    return n;
}

// трюк с масками, он же SWAR: складываем биты парами, потом тетрадами
int popcount_swar(uint32_t x) {
    x = x - ((x >> 1) & 0x55555555u);
    x = (x & 0x33333333u) + ((x >> 2) & 0x33333333u);
    x = (x + (x >> 4)) & 0x0F0F0F0Fu;
    return (int)((x * 0x01010101u) >> 24);
}

// и то, во что это превратилось
int popcount_today(uint32_t x) {
    return std::popcount(x);
}
```

На четырёх миллионах слов наивная версия занимает около 35 миллисекунд, трюк с масками 2,4 миллисекунды, а `std::popcount` 1,1 миллисекунды, то есть аппаратная инструкция быстрее наивного цикла примерно в тридцать раз. Но если пересобрать то же самое с `/arch:AVX2`, то `std::popcount` остаётся на своих 1,0 миллисекунды, а трюк с масками уходит на 0,8 миллисекунды и обгоняет уже аппаратную инструкцию. Причина в том, что `POPCNT` скалярная и берёт по одному слову за раз, а арифметика из SWAR прекрасно векторизуется, и компилятор считает биты сразу в 256-битных регистрах. Так что «опустили в железо» не всегда означает «стало быстрее», и расширение базы в ширину может проигрывать специализированным примитивам.

> AVX-512 (Knights Landing в 2016, Skylake-X в 2017) добавил 512-битные регистры `zmm`, вмещающие шестнадцать чисел `float32`.



### 2020-е: матрицы и примитивы для нейросетей

AVX-VNNI (2021, Alder Lake) добавил инструкцию `VPDPBUSD` и её вариации, чтобы считать скалярное произведение `int8` и `int16` с накоплением в `int32`. Теперь один вызов заменяет внутренний цикл свёртки, и нужно это для запуска нейросетей прямо на процессоре, без видеокарты.

```cpp
// свёртка на int8 с накоплением в int32, как в инференсе сети
int32_t dot_scalar(const uint8_t *a, const int8_t *b, std::size_t n) {
    int32_t acc = 0;
    for (std::size_t i = 0; i < n; i++)
        acc += (int32_t)a[i] * (int32_t)b[i];
    return acc;
}

static int32_t hsum(__m256i v) {          // сложить восемь дорожек
    alignas(32) int32_t t[8];
    _mm256_store_si256((__m256i *)t, v);
    int32_t s = 0;
    for (int k = 0; k < 8; k++) s += t[k];
    return s;
}

// то же самое, но по 32 пары байт за одну инструкцию
int32_t dot_vnni(const uint8_t *a, const int8_t *b, std::size_t n) {
    __m256i acc = _mm256_setzero_si256();
    for (std::size_t i = 0; i < n; i += 32)
        acc = _mm256_dpbusd_avx_epi32(acc,
                  _mm256_loadu_si256((const __m256i *)(a + i)),
                  _mm256_loadu_si256((const __m256i *)(b + i)));
    return hsum(acc);
}
```

Скалярная версия на восьми килобайтах данных занимает 26 миллисекунд, а версия с `VPDPBUSD`, как она написана выше, только 17, то есть выигрыш есть, но совсем не тот, которого ждёшь от аппаратной инструкции, делающей за один раз тридцать две пары умножений. Причина тут в «единственном» аккумуляторе, который вы передали в интринсик, и каждая следующая инструкция ждёт результата предыдущей, поэтому цикл упирается не в пропускную способность, а в ожидание данных. Если развести накопление по четырём независимым аккумуляторам, время падает до 5 миллисекунд, но та же свёртка на паре старых инструкций `PMADDUBSW` и `PMADDWD` с четырьмя аккумуляторами тоже укладывается в 5 миллисекунд. То есть опустить операцию в железо ещё не значит автоматически ускорить код. Конечно, специальная инструкция экономит опкоды и место в конвейере, но получить обещанный выигрыш вы сможете только когда сами уберёте зависимость по данным. Все замеры в главе сделаны на моём ноутбуке и числа здесь показательные, а на другом процессоре расстановка вполне может быть иной.

### наши дни...

Современные компиляторы уже живут в мире, где вычислительная база для фундаментальных типов очень богата и хорошо оптимизирована, а их основная задача состоит в максимально эффективном использовании этой базы, не ломая семантику языка. Поэтому когда вы пишете `a + b` для целых, компилятор уже знает, какую машинную инструкцию взять и какие флаги процессора она затрагивает.

## Как исправить `Fixed`

Вернёмся к делению в нашем типе из начала главы. Пятьсот снарядов, каждый делит скорость на что-нибудь порядка одной десятой, и цикл вычитаний прокручивается миллионы раз на каждое деление, поэтому это все обходится нам в секунды, что конечно же не подойдёт для реальной игры. Но выход есть, достаточно вспомнить правила целочисленного деления.

```cpp
struct Fixed {                        // тот самый тип из начала главы
    int32_t raw;
};

// деление на инструкции, которую 8086 принёс ещё в 1978 году
Fixed divide(Fixed a, Fixed b) {
    return Fixed{(int32_t)(((int64_t)a.raw << 16) / b.raw)};
}
```

И те же пятьсот делений теперь занимают 0,7 микросекунды, а результат, что важно, такой же бит в бит. Нужный нам детерминизм никуда не делся, ведь целочисленное деление округляет к нулю и делает это одинаково на любой платформе, а если вы попадёте на платформу, где 64-битного деления в железе нет, то правильным ответом будет деление в столбик по битам, тридцать два шага вместо миллионов. Выбор вычислительной базы это ведь не только «что есть в процессоре», но и «какой алгоритм вы поверх него положили».

## Что из этого следует для ваших типов

Вам это пригодится, если вы соберётесь писать операции для своего типа. Сначала надо разделить их на примитивы и производные и убедиться, что примитивы не собраны из циклов. Умножение через сложение и деление через вычитание это явно не лучшие варианты для реализации, а всё, что вы построите сверху, унаследует стоимость основания, и никакая оптимизация обёрток этого не исправит, и сложение через многократный `next` так и останется линейным и дорогим. Восемьдесят лет истории процессоров это готовый список операций, которые встречаются достаточно часто, чтобы их стоило иметь в базе, и для вашего `Fixed` будет достаточно посмотреть, что уже придумали за это время. Вы не первый, кто это проектирует, и это тоже хорошая новость, потому что большая часть граблей уже была собрана кем-то другим. Операции, которые логически выводимы, всё равно стоит добавить, даже если ими пользуются не каждый день, потому что цена одной строчки в интерфейсе типа несравнима с ценой десяти строк в каждом месте использования, но добавлять их стоит после того, как база стала эффективной, а не вместо этого. Красивый `operator<=`, под которым лежит цикл, всё равно будет «плохим кодом». И наконец, проектируя собственный тип, вы фактически повторяете путь архитекторов машин и авторов компиляторов. Выбираете, какие операции сделать базовыми, чтобы и алгоритмы выражались удобно, и компилятор порождал эффективный код. Разница в том, что у инженеров ранних процессоров этого выбора не было, а у вас есть... как есть и восемьдесят лет их опыта и опробованных решений.
