# Перегрузки

Итак, перегрузка в `C++`... её не учат в универе и не дают в книжках…

Начнём с истории. Живёт себе в проекте функция возведения в степень, написанная кем-то, проверенная временем и ни разу никого не подводившая, потому что всё это время она считала множители урона в `int` и в `float`. А потом проект переезжает на детерминированную арифметику с фиксированной точкой, на тот самый `Fixed` из прошлой главы, и её со спокойной совестью применяют к новому типу, ведь она же шаблонная, а значит обобщённая.

```cpp
struct Fixed { int32_t raw; };            // 16.16, тот самый тип из прошлой главы

Fixed operator*(Fixed a, Fixed b) {       // умножили и вернули точку на место
    return Fixed{(int32_t)(((int64_t)a.raw * b.raw) >> 16)};
}

template <typename T>
T pow_naive(T x, unsigned n) {
    T result = T{1};                      // <- а что тут теперь будет?
    for (unsigned i = 0; i < n; ++i)
        result = result * x;
    return result;
}

void damage_bonus() {
    Fixed per_stack{(int32_t)(1.1 * 65536)};     // +10% за стак, raw == 72089
    Fixed mult = pow_naive(per_stack, 13);       // ждём множитель около 3.45
    printf("raw=%d\n", mult.raw);                // raw=1, то есть 0.0000153
}
```

Это будет собираться, и даже как-то работать, но давать множитель урона примерно ноль. Дело в том, что `T{1}` для `Fixed` никакая не единица, а `raw == 1`, просто самое маленькое положительное число, какое этот тип умеет представлять. Умножение на такое число в формате 16.16 сдвигает результат на шестнадцать бит вправо, аккумулятор начинается с единицы младшего разряда и в ней же остаётся все тринадцать итераций.

Виноват тут не `Fixed`, не алгоритм и даже не программист, который их подружил, а наше допущение, что чужой тип будет вести себя как обычное целое, но, как говорил Джек Ричер, предположения убивают. К этому допущению мы ещё вернёмся в конце главы, а сейчас разберём, откуда у алгоритма вообще берётся право чего-то от типа требовать, и почему перегрузки в языке это не про красивые имена, и вообще не про имена.

## Сначала алгоритм, потом типы

Разговор о перегрузках стоит начинать не с синтаксиса и не с шаблонов, а с идеи построить такой интерфейс, который расширяется на новые типы данных и при этом остаётся понятным и рабочим. Сами авторы стандартной библиотеки сформулировали ключевую мысль так: сначала нужно правильно составить (придумать) алгоритм, и только потом понять, для каких типов он работает. Вы могли слышать эту фразу на конференциях или читать в книгах, но запоминать примеры из книг это отдельный навык, большинство примеров, что называется, прочитал и забыл... На практике же эта идея постоянно нарушается, и `pow_naive` из начала главы тоже её нарушил, поскольку алгоритм написали под конкретные типы `int` и `float`, а требования к общему типу на момент создания никто не выписывал. Давайте выпишем их, это недолго, всего лишь надо прочитать тело функции построчно и на каждой строке спросить, чего она хочет от `T`.

```cpp
template <typename T>
T pow_naive(T x, unsigned n) {
    T result = T{1};              // 1. у типа есть нейтральный элемент
                                  //    умножения, записываемый как T{1}
    for (unsigned i = 0; i < n; ++i)
        result = result * x;      // 2. есть operator*, из двух T даёт T
                                  // 3. результат можно присвоить обратно
    return result;                // 4. значение копируется наружу
}
```

У меня получилось четыре требования из четырёх строчек, и `Fixed` выполняет три из них: умножение мы ему написали, а присваивание с копированием достались от встроенного `int32_t`. Не выполняется только первое, и это довольно обычное явление, про специфичную инициализацию могут забыть, потому что для `int` и `double` она не даёт ошибок.

Посмотрите ещё раз на эти комментарии, видите, почему эту идею так часто нарушают? Несложно сделать алгоритм, но делая его из головы... очень легко начать с типов, классов «Weapon» и «Human», иерархий и других базовых вещей, понятных программисту, а уже потом пытаться «натянуть сову на глобус», то есть алгоритм на данные. Но обобщённое программирование подразумевает противоположный путь.

Не поленитесь открыть код алгоритмов стандартной библиотеки, вы увидите, что они максимально обобщены, и один алгоритм обслуживает и простые целые, и строку, и сложный класс, *если* у него есть нужные операции **с нужной семантикой** (регулярность, нейтраль, осмысленное сравнение и т.д., см. предыдущие главы). То есть одних перегруженных операторов будет достаточно, чтобы собралось, но маловато, чтобы `sort` и `accumulate` не посчитали ерунду.

Поэтому, берясь за алгоритм, надо отвлекаться от конкретных типов данных и спрашивать себя не «что это за объект», а «какие операции над ним нужны и что они обязаны гарантировать». Требования тогда становятся следствием алгоритма, а не свойством типа, который под руку подвернулся.

## Тип подходит синтаксически

`float` для скорости и многих других вещей подходит «синтаксически», потому что это число, его можно складывать и умножать, но семантически он неверен, потому что вместе с типом `float` мы теряем информацию о физическом смысле.

```cpp
void naive_physics() {
    float acceleration = 9.8f;   // м/с²
    float velocity = 100.0f;     // м/с
    float mass = 50.0f;          // кг
    float dt = 2.0f;             // с

    // Компилятор позволяет писать бессмыслицу
    float nonsense1 = acceleration + mass;      // 9.8 + 50 = ???
    // складываем м/с² с кг, физически это абсурд

    float nonsense2 = velocity * mass;          // 100 * 50 = ???
    // получили кг·м/с, но это импульс, а не ускорение

    float nonsense3 = acceleration / velocity;  // 9.8 / 100 = ???
    // получили с⁻¹, частоту, не имеющую отношения к задаче

    float nonsense4 = velocity + dt;            // 100 + 2 = ???
    // а тут сложили скорость и время, и всё опять собралось

    // Собирается всё, а сигнала об ошибке смысла нет, на выходе
    // просто неверные числа, без ассертов и без ошибок компиляции
    printf("%.1f %.1f %.1f %.1f\n", nonsense1, nonsense2, nonsense3, nonsense4);
}
```

Лечится это «строгими типами», приходится заводить типы, которые помнят смысл, и делать перегрузки, которые задают правила, а код от этого становится толще (bloated). Обратите внимание, что перегрузка ниже не «называет разные вещи одинаково», она возвращает разные типы, то есть у неё есть смысл, а не только форма.

```cpp
struct Seconds { float v; };
struct Metres  { float v; };
struct Speed   { float v; };     // м/с
struct Accel   { float v; };     // м/с²

Speed  operator*(Accel a, Seconds t) { return Speed{a.v * t.v}; }
Metres operator*(Speed s, Seconds t) { return Metres{s.v * t.v}; }

void typed_physics() {
    Accel g{9.8f};
    Seconds t{2.0f};

    Speed v = g * t;         // 19.6 м/с, тип поменялся вместе со смыслом
    Metres path = v * t;     // 39.2 м пути на постоянной скорости

    // Accel oops = g * g;   // перегрузки для такого нет, и это хорошая новость
    // Metres bad = v;       // и так тоже не соберётся, метры это не скорость

    printf("%.1f %.1f\n", v.v, path.v);
}
```

## Классический пример про перегрузку из учебника

А теперь посмотрим, как перегрузку обычно подают в учебниках, думая в рамках типов «у нас есть `int`, `double`, `string`, напишем функцию для каждого».

```cpp
// три функции, одно имя и ни одного алгоритма
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }
string add(const string& a, const string& b) { return a + b; }
```

Придуманный набор перегрузок становится способом называть похожие вещи одинаково, чтобы программисту не приходилось запоминать `add_int()`, `add_double()`, `add_string()`. Удобнее, чем три имени, кто бы спорил, но это поверхностное понимание, которое не выводит программиста за рамки процедурного мышления, и обобщённым программированием, которое вы видите в std, когда лезете в алгоритмы, оно не становится. Это просто синтаксический сахар, маскирующий набор отдельных функций под единым именем, и для четвёртого типа придётся дописать четвёртую копию `a + b`.

## Обобщение алгоритма

В `Notes on Programming` Степанов пишет, что школа структурного программирования (Дейкстра, Вирт, Хоар, Даль) его увлекла, но в ассемблере следовать советам было сложно, пока не пришло понимание, что идеи структурного программирования не привязаны к конкретному языку. Классический учебный сюжет про степень `x^n` Степанов разбирает в духе Гриса и Дейкстры, хотя сам алгоритм «возведение через квадрат» старше и шире исследований этих авторов.

Самое первое решение, которое обычно приходит в голову, это завести переменную-аккумулятор и n раз умножать её на x в цикле. Это `pow_naive` из начала главы, его легко объяснить, легко написать и легко проверить, и его часто предлагают на собеседованиях. Когда-то главным вопросом было «можно ли быстрее», ведь наивное решение пишут практически все. Можно, и уже очень давно:

> **Около 200 года до н.э.** Древнеиндийский учёный Пингала в своём трактате о стиховедении («Чхандах-сутра», в литературе она же «Чхандах-шастра») исследовал комбинаторику поэтических размеров, используя короткие (*лагху*) и длинные (*гуру*) слоги. Позиционной двоичной арифметики с нулём там ещё нет, но перечисление комбинаций слогов это уже двоичные разряды, а правила перехода от номера комбинации к самой комбинации и обратно известны в основном по комментарию Халаюдхи, это уже X век. Кнут разбирает эту историю в `The Art of Computer Programming`, том 2, раздел 4.6.3, и отсчитывает возведение в степень через квадрат как раз оттуда.

> **1976 и 1981.** Дейкстра, `A Discipline of Programming`, и Грис, `The Science of Programming`. Школа структурного программирования ставит программу и её доказательство рядом, и у Гриса быстрое возведение в степень разобрано как учебное упражнение на инвариант цикла, потому что интересно уже не «как написать», а «как доказать, что написанное верно».

> **2009.** Степанов и Мак-Джонс, `Elements of Programming`. Степень выведена не для чисел, а для любой ассоциативной операции, и вот это то самое слово, которого не хватает в учебниковой формулировке.

Алгоритм, который называется возведением в степень через квадрат (exponentiation by squaring), опирается на двоичное представление показателя степени и позволяет решить задачу за логарифмическое время. Вместо того чтобы делать n умножений, мы делим показатель пополам и возводим основание в квадрат, а если текущий показатель нечётный, то дополнительно домножаем результат на текущее значение основания.

```cpp
template <typename T>
T pow_fast(T x, unsigned n) {
   T result = T{1};

   while (n > 0) {
       if (n & 1)
           result = result * x;

       x = x * x;
       n >>= 1;
   }

   return result;
}
```

В программировании любое целое число можно представить в двоичном виде, а значит, любую степень можно разложить на произведение степеней двойки. Например, x в степени 13 это x в восьмой, умноженное на x в четвёртой и на x в первой. Алгоритм последовательно «пробегает» по битам показателя, начиная с младшего, и каждый раз решает, участвует ли текущее основание в конечном результате.

```text
x^13 = x * x * x * x * x * x * x * x * x * x * x * x * x   (13 множителей)

13₁₀ = 1101₂ = 8 + 4 + 1,  то есть  x^13 = x^8 * x^4 * x^1

x^1 = x                    (0 возведений в квадрат)
x^2 = x^1 * x^1 = x²       (1 возведение)
x^4 = x^2 * x^2 = x⁴       (2 возведения)
x^8 = x^4 * x^4 = x⁸       (3 возведения)

цикл идёт по битам от младшего к старшему:

   номер бита:   0     1     2     3
   бит числа 13: 1     0     1     1
   квадрат:     x^1   x^2   x^4   x^8
   участвует:   да    нет   да    да
                 ↓           ↓     ↓
        R  =    x^1    *    x^4 * x^8  =  x^13

   3 возведения в квадрат + 3 умножения в аккумулятор = 6 операций
   против 13 у наивного цикла (код выше делает ещё одно возведение
   в квадрат сверх этого, к нему мы вернёмся отдельно)
```

Теперь возведений в квадрат нужно столько, сколько в показателе значащих бит без одного (в коде выше их пока на одно больше, лишний квадрат мы уберём чуть ниже), а умножений в аккумулятор столько, сколько в нём единичных бит. Для n = 13 это 13 умножений против 6, для n = 100 сто против девяти, для n = 1000 тысяча против пятнадцати, а для миллиона миллион против двадцати шести.

## Что алгоритму нужно от типа

Как вы уже поняли, чтобы сделать хороший, удобный и правильный алгоритм, смотреть надо не столько на сам алгоритм, сколько на то, что ему требуется от типа данных. Алгоритму не важно, является ли `x` целым числом, вещественным, очень маленьким или очень большим целым (`int8_t` или `__int128`), матрицей или чем-то ещё. Ему нужно, чтобы существовала операция умножения, чтобы был нейтральный элемент этого умножения, и чтобы значения можно было копировать. Тут не хватает пары пунктов, и как раз про них забывают чаще всего.

Первый пункт это ассоциативность. Быстрый алгоритм не просто умножает в другом порядке, он умножает другие пары, ведь вместо x·x·x·… он теперь считает квадраты и собирает ответ из них. Второй пункт в списке вроде бы уже есть, это нейтральный элемент, только записан он там слишком неявно, `T{1}` и поехали. Нейтральный элемент есть не у типа, а у операции, и записать его литералом получается только у встроенных чисел. У `Fixed` единица это `raw == 65536`, а `Fixed{1}` это 2⁻¹⁶, у матрицы поворота 2×2 единица это `{1, 0, 0, 1}`, а `Mat2{1}` это `{1, 0, 0, 0}`, то есть проектор, который съест половину матрицы.

Проверяется это в пару строк кода: поворот на 90 градусов в четвёртой степени обязан дать единичную матрицу, и с настоящей единицей он её и даёт, а с `T{1}` возвращает `{1, 0, 0, 0}`. Что с этим делать, разберём позже, и тогда станет понятно, почему у некоторых алгоритмов есть специальные требования под входные аргументы.

Третий пункт (хм, обещал же два) в списке требований обычно не пишут, но он есть. Посмотрите на `pow_fast` ещё раз, строчка `x = x * x` стоит до сдвига `n >>= 1` и выполняется всегда, в том числе когда последний значащий бит уже обработан и результат готов. То есть алгоритм требует от типа помнить значение, которого в ответе нет, но у `Fixed` 16.16 множитель 1.5 в семнадцатой степени это 985.26 и такое число влезает с запасом, а вот лишний квадрат считает 1.5 в тридцать второй, и это уже 28 274 844 190 в единицах `raw`, что в `int32_t` не влезает, а наивный цикл на тех же данных не переполняется.

> Ещё внимательный читатель может вспомнить про коммутативность, но давайте сделаем это домашним заданием? Расскажу немного, чтобы подогреть интерес к теме. Коммутативность тут не нужна, множители все из одного и того же `x` и порядок алгоритм не путает, поэтому матрица из конца главы ему подходит, хотя `A * B` и `B * A` у матриц разные. Для целых перестановка пар не меняет ничего, но для `float` уже меняет, потому что умножение вещественных ассоциативно только в учебнике. На моей машине я прогнал 12 600 пар «основание, показатель», где основание идёт от 1.001 до 1.2 с шагом 0.001, а показатель от 2 до 64, и `pow_naive` с `pow_fast` разошлись в битах на 10 941 паре, то есть в 86.8% случаев.
>
> Для `1.1f` в сотой степени наивный цикл даёт 13780.6357, а быстрый 13780.6475, ошибка, возможно, невелика, но она есть, и если клиент считает множитель одним способом, а сервер другим, то вы получаете рассинхрон из предыдущей главы, без видимых причин. С `Fixed` будет то же самое, потому что усечение при обратном сдвиге тоже не ассоциативно, и на 1.1 в тринадцатой степени наивный вариант даёт `raw == 226210`, а быстрый `raw == 226213`.

Или вот целые: `pow_fast(2, 16)` для `int` возвращает правильные 65536, но по дороге вычисляет 65536 * 65536, что будет уже переполнением знакового целого, и формально это будет неопределённое поведение. Да, компилятор, скорее всего, выбросит это мёртвое умножение на `/O2`, если показатель известен ему на этапе компиляции, но вот когда показатель приходит из рантайма, то умножение остаётся в цикле как есть, и что случится при этом UB, мы сказать не можем, как и то, как оно повлияет на наш код. То есть опираться на такую догадку не стоит, тем более что чинится всё одной перестановкой.

```cpp
template <typename T>
T pow_fast_careful(T x, unsigned n) {
   T result = T{1};                // с этой строчкой разберёмся в следующей главе

   while (n > 0) {
       if (n & 1)
           result = result * x;

       n >>= 1;

       if (n)                      // квадрат нужен, только если впереди ещё биты
           x = x * x;
   }

   return result;
}
```

Разница в одну перестановку, но требования к типу уже стали другие. То есть надо всегда думать не про «алгоритм работает с любым типом, у которого есть `*`», а про «вот список того, что алгоритм делает с типом, проверьте, что ваш тип подходит».

## Почему это и есть перегрузки

И вот здесь мы выходим на связь с перегрузками и обобщённым программированием. Алгоритм у нас один, в коде выше это шаблон `pow_fast`, а конкретное умножение подбирается по типу, для `int` и `double` это встроенный `*`, а для `Fixed` и для матрицы это перегруженный `operator*`, который мы написали руками. Можно было бы вместо шаблона написать набор перегрузок `pow(int,…)`, `pow(Matrix,…)`, но суть та же, одно имя и один алгоритм при разных реализациях операции. Язык связывает абстрактный алгоритм с конкретными типами как раз через перегрузку операций (и функций) плюс шаблоны.

```cpp
struct Mat2 { int a, b, c, d; };           // повороты и отражения на сетке

Mat2 operator*(Mat2 m, Mat2 n) {           // тот самый «перегруженный оператор»
    return Mat2{m.a * n.a + m.b * n.c, m.a * n.b + m.b * n.d,
                m.c * n.a + m.d * n.c, m.c * n.b + m.d * n.d};
}

template <typename T>
T pow_fast_careful(T x, unsigned n) {      // алгоритм из середины главы, слово в слово
   T result = T{1};

   while (n > 0) {
       if (n & 1)
           result = result * x;

       n >>= 1;

       if (n)
           x = x * x;
   }

   return result;
}

void one_algorithm() {
    printf("%d\n", pow_fast_careful(3, 5));            // 243, тут T{1} угадал

    Mat2 rot{0, -1, 1, 0};                             // поворот на 90 градусов
    Mat2 r4 = pow_fast_careful(rot, 4);                // четыре поворота, ждём единичную
    printf("{%d %d %d %d}\n", r4.a, r4.b, r4.c, r4.d); // {1 0 0 0}, а не {1 0 0 1}
}
```

Умножение подставилось правильно, ведь именно для этого перегрузка операторов и придумана, а единица не подставилась. Формально и её можно подставить, дописав в `Fixed` конструктор от `int`, который сдвинет значение на шестнадцать бит, и тогда `T{1}` начнёт означать единицу. Только это опять будет соглашением, а не требованием, и компилятор его не проверяет и никакого `operator 1` в языке нет.

А для агрегата вроде `Mat2` конструктор придётся писать руками, потому что `Mat2{1}` это инициализация первого поля. Для матрицы, размер которой известен только в рантайме, не спасёт и такой конструктор, потому что единичная матрица зависит от размера операнда, то есть от значения, а не от типа, и придумать её внутри алгоритма нельзя в принципе.

Вот по этой линии обобщённый код и ломается чаще всего, и именно поэтому у `std::accumulate` начальное значение передаётся снаружи. Кстати, если полезть смотреть, как со степенью обошлась стандартная библиотека, то целочисленной перегрузки у `std::pow` нет, а целые аргументы приводятся к `double`, считаются там и возвращаются как `double`. То есть `pow(3, 38)` это не тридцать восемь умножений целых, а поход в вещественную математику, где за пределами 2⁵³ точный ответ уже не гарантирован, ведь не всякое целое там представимо, и на моей машине оттуда приходит 1350851717672992000 вместо 1350851717672992089, то есть мимо на 89. Стандартная библиотека богата на перегрузки, но не обязана иметь всё, что вам нужно.

И получается, что перегрузки (в широком смысле, и функций, и операторов) становятся не просто способом избежать разных имён, а механизмом идеи «один алгоритм для разных типов, если типы удовлетворяют требованиям». Это уже не побочное «удобство», а рабочий инструмент обобщённого программирования рядом с шаблонами и (позже) концептами.

## Что из этого следует для ваших алгоритмов

- Прежде чем называть шаблон обобщённым, выпишите список того, что он делает с типом. Не «нужен `*`», а «нужен ассоциативный `*`, нужен нейтральный элемент, нужен запас на лишний квадрат» и так далее.
- Нейтральный элемент `T{1}` работает только для встроенных чисел, а для вашего типа вернёт мусор, и договориться, что литерал означает единицу, можно, но проверить это соглашение компилятором нельзя.
- Если одну и ту же величину считают в двух местах, считайте её одним и тем же кодом. В примерах выше 86.8% пар разошлись в битах между двумя корректными реализациями одной и той же функции.
- Перегрузка операции это способ отдать типу его часть работы, оставив алгоритму форму, поэтому перегрузки живут рядом с шаблонами и концептами, а не в разделе «синтаксический сахар».

Если держать эти простые, действительно простые, ограничения в голове, то проектирование интерфейсов и алгоритмов начинает выглядеть иначе и вы начинаете думать не о классах и иерархиях, а о смысле операций и о том, какие свойства типов делают алгоритм корректным и эффективным. Т.е. начинаете думать в стиле стандартной библиотеки и обобщённого программирования, как это предполагалось авторами языка. А функция из начала главы так и осталась сломанной в одном месте, где мы предположили, что у всех типов есть единичное значение. В следующей главе мы посмотрим, как это исправить.
